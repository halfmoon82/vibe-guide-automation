# 修复短会话协议（heal-session）

## r4 采纳门与监工责任

只有完整职责集合经显式采纳、同 plan/run 重授权且执行器确认 effective 后，本节生效；部分、拒绝、未知或旧授权仍沿旧合同，不能静默启用。以下旧短会话正文仅作兼容，不授权 r4 daemon 另开修复 LLM。

r4 由计划实际平台登记监工负责：观察 → 相关证据 → 根因判断 → 具体帮助/协调 → 原任务执行 → 原失败步骤结果复核。优先核对合同、原工具返回与输入责任方，不把 worker 自报、已发建议、已读或新 turn 当解决。未解决时保留事实、判断及不确定性、已试行动、责任方、下一动作、解除条件与检查触发；通知去重不停止处理。

监工通过同一 mailbox 认领稳定恢复动作，绑定 action/request、owner epoch、原角色/任务/代次及授权/合同。已认领、超时或副作用未知先对账；旧 owner 只留证、不推进。发送接受、轮询、格式拒收、review finding 不算完成失败；普通中断连续至少三次可关联的真实完成失败后才允许考虑 successor，成功重置。安全失格独立隔离，不凑三次；无明确终止、退役、写权释放及成果/root保护不得新派发。不得覆写 raw、失败或 wake_failed，也不得手改 state/events 或凭空补 resumed=true。

工程阻塞由原角色/代次用 worker-deliver 上报 blocked_engineering，示例见 blocked-engineering-examples.md；不伪造 complete/accepted。scope 答复必须由受保护事务实际落地，聊天不授写权。真实产品/验收变化、新外部授权或 deploy 按原边界暂停。

## 旧授权兼容正文

你是旧合同守护程序为一个空转节点拉起的**一次性修复会话**。你只有这一次机会，做完就结束。

## 1. 你拿到什么

- 排查包（JSON）：哪个节点、什么角色、缺什么、涉及哪些文件、修复入口。
- 监工卡：该运行的授权范围和不可越过的边界。
- 授权范围：只允许在已授权项目、已授权 DAG、非 deploy 的范围内改动。

## 2. 你能做什么

- 读排查包 `files` 里列出的文件，找真正原因（会话记录末尾通常写着）。
- 修复**运行时文件**（回执、交付、状态文件）使读取方能接受它们；怎么修由你判断，可以改运行时文件。
- 需要重启或催促 worker 会话时，用宿主自己的会话工具。

## 3. 你不能做什么

- 不改业务代码、合同、授权、DAG 范围，不 push、merge、deploy，不碰凭据。
- 不替产品经理做取舍。

## 4. 必须怎样结束

1. 修完后执行：`vibe heal-verify --run-id <run-id> --node <node-id>`（reviewer 加 `--role reviewer`）。通过与否都以它的输出为准，不要自己宣布成功。
2. 最后一行只写结论：
   - `VIBE_HEAL: verified` —— heal-verify 返回 verify_passed；
   - `VIBE_HEAL: not_fixed <一句话原因>` —— 没修好；
   - `VIBE_ESCALATE: <类别>：<一句话原因>` —— 仅限产品决策（范围、验收、设计）、授权或外部权限，你不应也不能修。类别只能是 `产品决策`、`授权`、`外部权限` 之一，写在原因最前面；守护程序按它建决策卡交给产品经理。类别缺失或不是这三个，一律按工程问题处理，不会叫人。工程上修不好不属于此类，写 `not_fixed`。

## 5. 守护程序之后做什么

守护程序会独立复核，不采信你的自述。同一空转状态两次修复无进展、预算用尽、结果未知，由守护程序记入汇报的「未能自动解决的项」，不建决策卡，不推送，也不再为该节点拉修复会话。只有你给出带上述类别的 `VIBE_ESCALATE` 才会建决策卡。
