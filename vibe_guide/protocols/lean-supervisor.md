# Vibe Guide · 轻监工协议（lean 档，宿主 agent 用）

> 随 vibe 包发布，按需读取：入口判为 `execution_tier=lean` 时只读本文件，不同时读完整监工协议。完全自包含。
> 机制来源说明：只借鉴 Akasha 监工的机制思路，不复用其受保护文本或脚本（许可为 Apache 2.0 加商业条件，且项目规则禁止复制 Skill 源码）。

## 1. 适用与边界

- 适用：有真实委派/独立审查收益、但一张小任务板足以管理的工作；常见 1–4 个业务节点、短周期，或单个长串行 writer。
- 不适用：需要持久跨节点验收、在途动作对账、多波硬依赖重算时，升级到 `run`（§6）。
- 轻不是弱：授权卡、独立只读验收、设计稿门、真实授权三档都一样，本协议不豁免任何一项。
- 目标不清或有产品取舍，先澄清，不以「轻」跳过。

## 2. 最小合同（每节点一份，写进任务板）

- `目标与验收例子`：一句话目标，至少一个可判定的验收例子。
- `写范围`：节点允许改的文件清单；一个节点只允许一个有效 writer；范围重叠的节点先合并或串行。
- `拓扑与可见性`：默认「可见 developer＋独立只读监工验收」；项目规则要求两个独立可见任务时，在规则与授权明确修订前继续遵守，不擅自互换。
- `并发与外部动作`：并发上限、是否含 Git 远端动作组；deploy、凭据、系统权限永远单独授权。

任务板只记节点状态、任务身份（provider、任务 ID、worktree、分支、续接 cursor）和证据路径，不是第二个 DAG 引擎，也不是第二套任务状态：沿用现有任务登记、信箱和状态原子写。

## 3. 授权：紧凑授权卡

涉及监工、并行开发或外部动作时，仍展示授权卡，只是紧凑：目标/验收、节点与写范围、拓扑与可见性、并发、外部动作权限。用户明确确认后才开工；范围或拓扑变化使旧授权失效。不另建弱化的授权体系。

## 4. 执行与等待

- 启动所有无硬依赖冲突的节点；等待时静默，不轮询、不重复读全量历史。
- 续接只读 P1b 的薄上下文与续接差异（水位之后的新事件），不重放全量历史；绑定的继续/返工/心跳/接班走快路径，不重评分、不读规划协议。
- 唤醒时先用本地机械层过滤：无变化不入模；新故障、到期事项、授权版本变化必须唤醒。
- 未知状态保持 `blocked_unknown` 并写明原因，不当成成功或无事项。

## 5. 独立验收与有界返工

- 独立验收：只读审查，不得代改业务代码，不能由 developer 自审代替。
- 缺陷退回同一 developer，复审回到同一 reviewer，保留身份、cursor 和证据链。
- 同一节点实质返工 3 轮、第 3 轮复审仍有 P0–P2：不发第 4 轮，自动换新 worker 接力（旧 writer 确认停止、成果封存后再派），节点累计成本不超过授权上限。
- P0–P2 清零、证据登记完成后才算验收；合并、deploy 按各自授权。

## 6. 升级到 run

出现任一事实时停下、保留成果/任务身份/证据，补齐业务合同、DAG 与授权，再按完整流程继续：

- 节点数或并行度超出小任务板能管（多波硬依赖、中断后需重算 ready）；
- 上游验收被撤销需阻断并重验下游；
- 多个在途副作用需跨会话对账，或跨节点共享批准需可追溯变更。

涉及拓扑或任务可见性变化时，按项目规则使旧授权失效并确认后续范围。

## 7. 不做什么

- 不为凑完整流程拆假节点，不为分数强拆单节点；不强制完整 PRD 编写、完整 DAG 审计、频繁换班和定时新会话。
- 不把评分、档位或入口回执当成授权；不把测试通过、PASS 当成业务批准。
- 不替用户做产品决策；工程问题自行决定并记入证据。
