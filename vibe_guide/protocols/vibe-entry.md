# Vibe Guide · 新会话入口协议（宿主 agent 用）

> 本文件随 vibe 包发布，由 `vibe init --confirm` 物化到 `.vibe/proposals/skills/vibe-entry/SKILL.md`；物化后 vibe 永不改写它，你的本地修改在重复 init 后存活。
> 面向 Claude Code / Codex 等宿主 agent。**完全自包含**：只装 vibe 即可完整执行本协议，不依赖任何外部技能。

## 0. 分工与适用边界

- 本协议只做一件事：**新会话收到请求后的入口自评与路由**——会话内完成 S0/S1 判断，只有确认为复杂的请求才调用 vibe CLI。
- 被判为复杂之后的路径（PRD 引导、节点拆分、授权卡、监工）按 `.vibe/proposals/skills/prd-guide/SKILL.md` 执行；本协议不重复其内容。
- 宿主已装 `complex-task-methodology` 技能时，可（可选）用其完整评分表替代 §2 的速查表；未装不影响本协议任何一步。
- 纯问答、翻译、解释、单次查找、继续/确认类请求不启用本协议，直接回答（§4 已挂起的设计稿门除外）。「排查」类请求含只读的日志/生产数据分析与诊断定位，不在此白名单内。

## 1. S0 白名单（零成本，直接执行）

命中以下任一类型 → 直接做，不评分、不调 vibe：

| 类型 | 例子 |
|---|---|
| 简单问答 | 「什么是 X」「解释这段代码」「翻译这句话」 |
| 继续/确认 | 「继续」「好的」「然后呢」 |
| 单次查找 | 「帮我搜 X」「读一下这个文件」 |

有实现意图、跨文件、或路径不明 → 进 §2 评分。

「继续」「好的」这类回复走白名单，但**不解除 §4 已经挂起的设计稿门**：门没过，就还不能动手改界面。

## 2. S1 五维评分（会话内完成）

五维以 vibe planner 的 `TaskContext` 为唯一真相源，字段名与顺序固定为 `steps`、`domains`、`uncertainty`、`failure_cost`、`toolchain`：

| 维度 | 1 分 | 3 分 | 5 分 |
|---|---|---|---|
| `steps` 步骤数 | 1-2 步 | 3-5 步 | 6 步以上 |
| `domains` 知识域 | 单一文件/模块 | 跨模块 | 跨系统/架构级 |
| `uncertainty` 不确定性 | 路径明确 | 部分需调研 | 大量未知 |
| `failure_cost` 失败代价 | 可随时回退 | 中等影响 | 不可逆/影响生产 |
| `toolchain` 工具链复杂度 | 现有工具即可 | 需新装/新配 | 多工具编排 |

每维取 0-5 整数，表中为 1/3/5 锚点：0 表示该维度可忽略，2/4 为相邻锚点之间的中间档。

阈值（与 vibe planner 路由一致）：

- **<=8**：直接执行，不触碰 vibe。
- **9-15**：轻规划（列出步骤要点），不触碰 vibe。
- **>15**：进 §3 的 vibe 正式路由。

凡经过本节评分的请求，评分后必须先输出一行可验证的 S1 结果再行动，形如 `S1：11→轻规划（不触碰 vibe）`（<=8 为 `S1：8→直接执行（不触碰 vibe）`；>15 为 `S1：17→vibe 正式路由`；拿不准时给区间估计并标注「拿不准」，按 >15 处理）。宿主自有强制入口/状态行/卡片协议时，把该行并入其首个强制状态行作为 `S1：` 字段，不另起一行、一轮评分或第二个门。

防呆与动态升级：

- **拿不准一律按 >15 处理**进 §3——误进复杂无害，误放简单危险。
- 执行中出现以下任一情况，停下来重新评分并升级档位：同一方案连续失败 2 次以上；实际步骤数超过预估 2 倍；发现意外的阻塞依赖；发现影响共享/生产系统。

## 3. 复杂路径（>15 或拿不准）

```bash
vibe scan --json                                        # 只读：确认项目态与会话门
vibe plan --request "<用户原话>" --s1 5,3,5,3,1 --json    # 正式路由；示例为 17 分（五维顺序见下）
```

- `--s1` 五个数字的顺序即 `steps,domains,uncertainty,failure_cost,toolchain`，各取 0-5 整数。
- `route` 为 `simple`/`light_plan`：按 vibe 的路由结果直接执行（vibe 的正式路由优先于你的自评）；涉及图形界面时，动手前仍先过 §4 设计稿门。
- `route` 为 `complex`：记下 `plan_id`，按 prd-guide 协议进入 PRD/Spec/DAG/授权卡流程。
- **首班监工开工两件事**：`route` 为 `complex`、监工（`vibe monitor`）真正启动之后，本会话作为首班监工必须先做这两件事，做完才算开工——`vibe supervisor-register --run-id <run-id> --provider <平台> --session-id <本会话 id> --host <本机标识>` 登记自身地址；再用宿主平台原语自建心跳，心跳第一步固定跑 `vibe supervisor-preflight --run-id <run-id> --session-record <本会话记录路径>`。不登记，worker 的完工唤醒信号无处可发；不建心跳，`rotate` 的换班检测不会发生。两条指令的完整说明见 prd-guide §6.0。
- **会话门阻塞（`session_gate_blocked`）时必须停下报告**，不得伪造状态、不得跳过门禁、不得手写 plan 工程字段。
- scan 报告未知/超时保持 `unknown`，不得当成成功或永久不可用。

## 4. 界面设计稿门（与评分无关，始终生效）

只要请求会新增或改动人会看到、会操作的图形界面（页面、弹窗、表单、面板等），**不管 S1 多少分**，都先过这道门：

- **列全页面**：写出本次新增和改动的每一个页面，每个页面一份设计稿，不能只给其中几页。
- **设计稿必须打开就能看到页面长什么样**：图片、HTML 原型、Figma 等设计工具链接都可以；**纯文字描述不算设计稿**。在会话里以可点击链接给出。
- **产品经理明确确认之前，严禁动手写实现代码**，"先搭个架子""先写后端再补界面"都不行。设计稿改过就要重新确认。
- **路由不变，只是开工前多一道确认**：<=15 按原档位执行，但动手前先出稿、等确认；>15 走 §3，设计稿写进 PRD 的 `design_mockups` 小节（见 prd-guide §2）。
- **门的状态跨轮次保持**：出稿之后收到「好的」「继续」这类泛泛的回复，不算对设计稿的确认，也不解除这道门。确认要明确指向设计稿；拿不准就回问一句"这几页就按这版稿子做吗？"。
- **拿不准算不算改界面，按改界面处理。** 命令行输出、日志、接口字段这类没有图形页面的改动不在此列。
- 评分行后面加上门的状态，形如 `S1：6→直接执行（不触碰 vibe）；设计稿门：待确认`，确认后再开工。

## 5. 授权纪律（与评分无关，始终生效）

- commit / push / 创建 PR / merge 属 Git 远端动作授权组；deploy、发布、生产写入、凭据永远单独授权。
- 测试通过、PASS、文件存在都不是业务批准、发布或 merge 事实。

## 6. 短提示

项目已初始化且 Spec/计划/状态存在时，可使用短提示：「扫描适配」「初始化项目」「继续规划」「启动监工」「继续监工」。短提示不绕过需求决策、DAG 确认、授权与门禁。

## 7. 不做什么

- 不绕过任何门禁与授权边界；不替用户做产品决策；不在设计稿确认前动手改界面；不把自评分数当 vibe 的正式路由结果；不为简单任务调用 vibe（那是本协议存在的意义）。
