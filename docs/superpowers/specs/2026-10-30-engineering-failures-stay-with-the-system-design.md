# 工程故障留在系统内：升级分类、产品语言汇报与「搁置」状态设计

状态：待产品经理确认（未实现）。基线：origin/main 4b69de5。

## 1. 要解决的问题

监工和守护程序反复停下来，把工程问题抛给产品经理。产品经理不懂工程规范，这类问题他既答不好，也不该答；答不上来时整条线就停住（实际发生过：一个路径范围问题让 7 个节点停了十几个小时）。

已核实的四个来源：

| # | 来源 | 位置 |
|---|---|---|
| 1 | 守护程序 7 处升级里 6 处硬写 `product_acceptance`，把空转、预算用尽、修复结果未知、守护程序出错、暂停推进、运行停在 blocked 都变成「需要你处理」+ 决策卡 | `daemon.py` `_escalate` 各调用点 |
| 2 | 升级决策卡只有「继续让监工自愈 / 我来处理」，推荐后者，终点被设计成交给人 | `daemon.py` `_escalate` |
| 3 | 修复会话协议告诉会话「`VIBE_ESCALATE` 会转给产品经理」，且只有授权/产品两个出口 | `protocols/heal-session.md`、`daemon.py` `_level_two` |
| 4 | 已安装的 5.1.16 没有守护程序、`worker_questions`、短会话；监工无处答复 worker | 已安装包 |

#327（提示词规则）和 #328（后台 worker 禁用 `AskUserQuestion`）已合并，只管 worker 和提示词一侧，不管上面 1–3。

## 2. 设计原则（从产品经理出发）

产品经理只会被叫到三种场合，其余全部由系统消化并留痕：

1. **产品决策**：范围、验收、设计要变。
2. **外部动作**：充值、凭据、授权、部署，只有他能做。
3. **验收例子达不到**：系统穷尽办法后，PRD 里某个验收例子仍然过不了。

推论：

- 工程层可以无限自愈，边界是预算与时间，不是「次数」，也不交给人。
- 系统**不能自己放弃**一块功能。静默放弃等于悄悄缩小产品范围，那是产品经理的权力。系统可以「搁置」（暂停并继续别的），不能「放弃」。
- 对产品经理说话只用产品语言：哪个验收例子受影响、现在什么状态、有哪几个选择及各自的产品后果。工程细节放在展开里，不进正文。
- 任何一次打扰都必须给出选项，不能只报告问题。

## 3. 已核实的现状（设计依据）

- 运行状态判定 `_refresh_run_status`（monitor.py:9989）：只要有节点 `failed` 或 `stopped`，整个运行就是 `failed`；有 `blocked_unknown` 则运行是 `blocked_unknown`。守护程序 `TERMINAL_STATUSES` 含 `failed`（daemon.py:36），所以「标记节点失败」会让运行终止，其余节点不会继续。
- `blocked_unknown` 不使守护程序退出，但运行状态随之变成 `blocked_unknown`。
- 就绪集（monitor.py `_topology_projection`、dag.py `node_scoped_ready`）：`blocked_unknown / blocked_design / blocked_deploy` 的节点进入 `blocked_ids`，其硬依赖闭包被排除，**不相关节点仍会被调度**。已有测试证明（test_node_scoped_blocking.py::test_repair_wait_keeps_unrelated_ready）。所以「继续其余节点」在节点层面已经成立，缺的是运行层面的收口规则。
- 收口门 `evaluate_v41_closeout`（evidence.py:468）：要求**所有**业务节点 `accepted`、整合审查节点 `accepted`、证据齐全、P0/P1/P2 清零。没有任何「带缺口完成」的路径。
- 整合审查证据 `aggregated_scope.nodes` 必须**精确等于**运行里全部非整合节点（evidence.py:322-324）。一个搁置的节点要么在列表里（那它必须 accepted），要么不在（判「与运行冲突」）。
- 整合证据里已有 `unverified_or_excluded` 字段，但它只是记录，不会让收口门放行。
- 节点状态词汇有三处：`state.py _NODE_STATUSES`（运行快照）、`models.py _NODE_STATUSES`（DAG 模型，更窄）、`lifecycle.py` 的状态集（有测试 test_lifecycle_status.py 钉住差异）。新增状态要同步这三处和 `map_user_status`。
- 对用户可见的状态词表是固定七个（state.py:168）：准备中、自动修复中、已启动、需要你决定、需要监工建工作树、需要监工排查、需要人处理。未知状态一律显示「自动修复中」。
- 决策卡的答案动作表 `_ANSWER_ACTIONS`（monitor.py:191）把（原因，选项）映射成节点迁移，现有只有 4 个。
- 验收例子存在节点合同的 `acceptance_example` 字段里，每个节点一条；PRD 的 `goals[].dag_nodes` 把目标关联到节点。所以「节点 → 验收例子」有现成的映射，不需要新建。

## 4. 阶段一：升级分类与产品语言（只改守护程序和文案，不碰状态机）

### 4.1 分类

把 `_escalate` 的 `category` 参数收敛成两类，由调用点的**原因**决定，不再一律 `product_acceptance`：

| 原因 | 现在 | 改后 |
|---|---|---|
| 空转后修复无进展、预算用尽、修复会话结果未知、守护程序连续出错 | 建决策卡 + 推送「需要你处理」 | **工程类**：不建卡、不推送；写 `daemon_heal` 事件（`kind=engineering_unresolved`）并计入汇报 |
| 门禁拦截（授权失效、能力合同漂移等） | `product_acceptance` | 授权类 → 保持 `external_authorization`，建卡；其余工程原因同上 |
| 修复会话输出 `VIBE_ESCALATE` | 授权/产品二选一 | 保持建卡，文案改产品语言（见 4.3） |

判定规则是结构化的（原因码），不靠文字匹配。`needs_decision` 这一支按修复会话的标记走，授权判断沿用现有的关键词，但缺省不再落到 `product_acceptance`：拿不准时按工程类处理，不打扰产品经理。

### 4.2 工程类故障到汇报的路径

- 守护程序对仍未修好的节点写 `engineering_unresolved` 事件，带节点、验收例子引用、已试次数、原因码。
- 运行结束（收口或停止）时，汇报里单列「未能自动解决的项」，每项用产品语言（见 4.3）。
- `vibe status` 展示同一份列表。
- 不推送。唯一的推送仍是：运行结束、真正的产品/授权决策卡。

### 4.3 产品语言汇报格式

每一项只有四行，工程细节折叠：

```
受影响的验收例子：<该节点 contract.acceptance_example 原文>
现在的情况：<自动修复中 | 已多次尝试仍未达成>
你可以选择：
  - 调整这条验收（改变产品范围，需要你确认）
  - 接受缺口后继续（该功能不随本次上线）
  - 再给系统一轮
（展开：节点 <id>，已试 <n> 次，原因码 <code>）
```

选项文案要在文档里固定，不由模型自由发挥，防止每次说法不同。

### 4.4 同步修改

- `heal-session.md`：删除「推给产品经理并建决策卡」，改为「空转、预算用尽、未能修复由守护程序记入汇报」；`VIBE_ESCALATE` 的适用范围收窄到产品、授权、外部权限。
- 监工卡（supervisor-card.md）：`decision` 状态里的 `worker_questions` 由监工先自己答复，不呈现给用户。
- `prd-guide.md §6.1`：第三级描述同步。
- 三个协议文件改动要同步 `SHIPPED_PROTOCOL_DIGESTS`。

### 4.5 阶段一的风险（必须告知）

阶段一上线后、阶段二完成前，一个修不好的节点**不再叫人，也不会前进**，运行会安静地停着，直到汇报或你查看 `vibe status`。为避免沉默：运行在无进展状态持续超过时限（**上限 6 小时**，已由产品经理定，可配置得更短，不可更长）时，发一条**产品语言的汇报**（不是升级卡），告诉产品经理哪些验收例子还没达成。同一组未解决项只汇报一次，项目集合变化才再报；不按 6 小时周期重复推送。

**不空转烧 token（已核实）：** 守护程序每个周期只读盘，不调模型；只有二级修复短会话耗模型，硬预算 `max_sessions=6`、`max_tokens=500000`，同一节点修两次无进展即停，同一时刻最多一个短会话；监工心跳在指纹无变化时直接返回 `stop`。阶段一保留 `escalated` 标记（只是不再建卡），使放弃自愈的节点不会被反复拉起修复会话。6 小时汇报只读盘并发一条通知，不拉会话。

### 4.6 阶段一的测试

- 现有 `test_daemon_heal.py` 里 6 个断言升级的测试要改写，它们当前断言「推送一次 escalation + 建一张卡」。
- 新增：工程类原因不建卡、不推送、写事件；`VIBE_ESCALATE` 仍建卡；6 小时无进展汇报且同一组项目只报一次；放弃自愈的节点不再拉修复会话；汇报只含产品语言正文。

## 5. 阶段二：「搁置」状态与收口门（改状态机，需要你先批准）

### 5.1 新增节点状态 `deferred`（搁置）

含义：这个节点的验收例子目前达不到，**产品经理还没选**。不是失败，不是放弃。

- 进入条件：守护程序对该节点穷尽自愈（预算或时限用尽）后，由守护程序置位，并建一张**产品语言决策卡**（4.3 的三个选项）。这是阶段二里唯一会建卡的工程类路径，因为这时它已经变成了「验收例子达不到」，是产品决策。
- 搁置期间：
  - 节点的**硬依赖闭包**一并暂缓（沿用现有 `blocked_ids` → `dependency_closure` 机制，把 `deferred` 加进去即可），不相关节点继续跑。
  - 它占用的 worker 名额释放。
  - 它不算 `failed`，不触发运行级 `failed`，守护程序不退出。
- 退出条件，只有产品经理的选择：
  - 「再给系统一轮」→ 回到 `rework`，修复预算清零重新计。
  - 「调整这条验收」→ 走现有的产品决策流程改 PRD/合同，旧授权失效，重新授权（沿用既有规则）。
  - 「接受缺口」→ 进入下面的 `accepted_with_gap`。

### 5.2 新增终态 `accepted_with_gap`（带缺口接受）

含义：产品经理明确选择「该功能不随本次上线」，并留下了凭证。

- 只能由决策卡的答案产生，**系统不能自己写**。决策答案已有摘要绑定与 `--digest` 校验，直接复用。
- 它的依赖闭包保持暂缓，运行结束时一并列为缺口。

### 5.3 收口门的变化（核心）

现有规则：所有业务节点 `accepted` 才 `complete`。改为：

| 条件 | 运行最终状态 |
|---|---|
| 所有业务节点 `accepted` | `complete`（不变） |
| 有节点 `accepted_with_gap`，其余业务节点 `accepted` 或因闭包暂缓，且每个缺口都有对应的产品经理决策记录 | **`complete_with_gaps`**（新增，不等同 `complete`） |
| 有节点处于 `deferred`（产品经理还没选） | 不收口，运行保持 `running`，汇报里列出待选项 |
| 有节点 `failed` / `blocked_unknown` | 不变，仍是对应的运行状态 |

关键约束：

- `complete_with_gaps` 在所有对外表述里**必须和 `complete` 区分**，汇报首行写「已完成，但有 N 项功能未达成」，并逐项列验收例子。AGENTS.md §2 已要求「技术完成、Review 通过、交付授权、merge 和 deploy 分开表达」，这是同一条精神。
- 整合审查必须覆盖**所有**业务节点，包括缺口节点：`aggregated_scope.nodes` 仍等于全部非整合节点。缺口节点在 `unverified_or_excluded` 里必须出现并带产品经理决策 ID；整合审查对这些节点审的是「它没被合入、没有半成品泄漏进主干」，不是它的功能。
- 整合审查节点本身依赖缺口节点的部分，要把缺口节点从它的 `depends_on` 里按「已接受缺口」处理，否则它永远不 ready。这一点需要在 DAG 层明确，是阶段二最容易出错的地方。
- `evaluate_v41_closeout` 的 P0/P1/P2 清零要求**不放宽**。缺口不是缺陷豁免，是范围收缩，两者不能混。
- deploy 与 merge 的授权规则不变。`complete_with_gaps` 的运行，授权卡里列入的受限 merge 是否照样自动 merge，我建议**默认不自动 merge**，要产品经理再点一次（理由：带缺口的交付他应该最后看一眼）。这是一个需要你拍板的点（见 7）。

### 5.4 状态词汇同步

- `state.py _NODE_STATUSES`、`models.py _NODE_STATUSES`、`lifecycle.py` 状态集、`map_user_status`、`_RUN_STATUSES` 同步加入；`test_lifecycle_status.py` 里钉住的差异更新。
- 用户可见词表加两个：**「已搁置，等你选择」**（`deferred`）、**「已完成，有缺口」**（`accepted_with_gap` 节点 / `complete_with_gaps` 运行）。保持词表是小而稳定的集合，不再让未知状态落到「自动修复中」。
- 守护程序 `TERMINAL_STATUSES` 加入 `complete_with_gaps`；`deferred` 不加（守护程序要继续跑别的节点）。
- 归档（monitor.py:2705）的终态集合加入 `complete_with_gaps`。

### 5.5 阶段二要补的测试

- 搁置节点不影响不相关节点；依赖闭包被暂缓；名额释放。
- 三个选项各自的迁移，包括「再给系统一轮」预算清零。
- 收口门：全 accepted → `complete`；有缺口且有决策 → `complete_with_gaps`；缺口缺决策记录 → 不收口；`deferred` 未选 → 不收口。
- 整合审查覆盖缺口节点：`aggregated_scope` 一致性、`unverified_or_excluded` 带决策 ID。
- 崩溃重放：搁置和缺口的事件都进 `_EVENT_DATA_KEYS`（已知陷阱：不在允许名单里的事件字段落盘时会被丢）。
- 旧运行快照读取：没有新状态的旧快照照常读（已知陷阱：改词表让旧授权运行读不出，见 5.2.0 事故）。

## 6. 不做的事

- 不让系统自己放弃节点或自己写「接受缺口」。
- 不放宽 P0–P2 清零。
- 不改已安装的 5.1.16；需要升级到含守护程序的版本才生效，升级是单独动作。
- 不在聊天里做文字匹配来拦监工提问（误判多，收益低）；先看阶段一上线后监工是否还会自己问。

## 7. 产品经理已拍板（2026-10-30）

1. **`complete_with_gaps` 的运行不自动 merge**，要产品经理再确认一次。
2. **无进展汇报的时限最长 6 小时**（原建议 24 小时被否决，太长）。要求无进展时不空转烧 token，见 4.5 的核实结论。
3. **阶段一单独先上，阶段二设计通过后再做。** 两者之间有 4.5 说的安静期，由 6 小时汇报缓解。
4. **「再给系统一轮」连续 3 次封顶**，第 4 次起只剩前两个选项。
