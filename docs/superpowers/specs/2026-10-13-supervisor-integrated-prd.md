## 1. 问题

两次真实长运行（run 140：13 任监工、10.5 小时；样本 run：14 个节点完成 12 个后停住）暴露了三类问题，证据见 A 的附件与 issue #157：

1. **监工不推进**：worker 已交付或 provider 已返回，监工仍长期空闲、复读或进入 `blocked_unknown`；生命周期类审查意见被循环派回开发者。
2. **工程问题打断产品经理**：权限字眼、未知严重度、普通报错写永久授权失效、挂起不校验原因、宿主对齐门，都把纯工程问题变成「请产品经理决定」；需要产品经理拍板的决策又没有落点，跨 3→7 班靠交接文本口口相传。
3. **监工上下文与换班成本**：空闲心跳复述整轮状态，例行换班反复重放上下文，并带来多会话、半接管和权限退化。

## 2. 目标

| # | 目标 | 用户可见结果 |
| --- | --- | --- |
| G1 | 授权范围内自主推进 | 授权一次后离开电脑，节点按 DAG 推进到终态或唯一真实人类边界 |
| G2 | 只在产品边界打断 | 纯工程问题打断产品经理次数为 0（判据 B1） |
| G3 | 决策闭环 | 回来时看到一份待拍板决策清单；拍板后监工自动继续；监工接管后同一决策仍在 |
| G4 | 单班轻载 | 一个监工会话服务到底，空闲心跳上下文增长有上限，不例行换班 |
| G5 | 宿主一致 | Claude Code、Codex、WorkBuddy 上入口规则真实生效、拓扑判定正确、能力降级如实披露 |
| G6 | 入口分诊 | 入口请求先经分诊钩子，网关不可用时按现有 S1 规则兜底 |
| G7 | 可观测 | 每次进展、打断、接管、心跳和 token 都有可核对的记录 |

## 3. 非目标

- 不降低唯一 writer、独立 reviewer、授权绑定、真实系统权限与 deploy 单独授权等边界。
- 不做具体 IM bot、webhook server 或凭据存放；不暂停心跳。
- 不实现真实决策网关服务与评测集标注（B5）。
- 无同类对照与价格数据时，不宣称节省 token 或费用。
- 不删除已合入 main 的换班相关命令和数据格式（`supervisor-register`、`supervisor-preflight`、`supervisor-handoff`、`supervisor-hold`、`handoff-summary.json`、接班起点记录）。

## 5. 需求

### 5.1 进展与状态模型

沿用 A §4.1、§5：只有持久状态转换算进展；事件稳定可去重；宿主会话状态只是输入信号。新增事件至少包括 `decision.raised`、`decision.answered`、`decision.invalidated`、`notify.pushed`。

### 5.2 单班与唯一接管

- 按 D1 与 N3 运行；绝对上限沿用 M 的 20 万与 `--context-hard-cap`。
- 接管条件、事务步骤、权限继承、failed handoff 去向沿用 A §8。
- N 的「合法后台 successor 登记」并入 A §8 的唯一接管：successor 登记必须经过同一租约 CAS，不得形成第二条所有权路径。

### 5.3 心跳

- **指令形态**：vibe 生成一行规范心跳（#156），宿主逐字照抄；预检输出 `idle`、`work`、`decision`、`rotate`、`unknown` 五态。`decision` 只在「有未答决策且无其他可服务事项」时输出；有交付、结果、请求或 ready 节点时优先输出 `work`。
- **兼容规则**：新版心跳指令调用预检时传入 `--accept-decision`。预检只在带该参数时输出 `decision`；旧版指令调用时，同一情形输出 `work`，监工按旧流程 `resume`，由 `resume` 渲染决策卡片。既有四态测试保留；新增测试断言五态各有分支、旧版调用不会收到 `decision`。
- **间隔**：按 N1，单一来源；实现必须允许注入时钟或间隔参数，以便自动化验收。等答降频状态写在盘上，接管后的监工从盘上读到并恢复。30 分钟档只在该平台推送唤醒的真实验证报告（成功、失败各至少一次原始证据）登记后启用。
- **防复读**：沿用 A §6.3（连续 3 次无进度心跳不复述，触发一次恢复动作）。
- **空闲只读增量**：沿用 A §6.3 与 §11。

### 5.4 原生动作与结果

沿用 A §7（外层闭环、结果收件箱、竞态终态优先级、错误保真）。

### 5.5 决策信箱

按 issue #141 第一层设计，并作以下统一：

- 存储：`.vibe/decisions/{requests,results}/`，复用 provider 动作的四键绑定（`schema_version`、`decision_id`、`request_digest`、`payload`）。
- 两个入口：worker 交付中的 `decision_requests[]`；监工的 `vibe decision-raise`。两者同一信箱、同一上浮路径。
- 每条决策包含：问题、选项（id、说明、影响）、推荐、类别（N4）、证据绑定（run、节点、交付引用）。
- 回答：`vibe decision-list`、`vibe decision-answer --id --choice [--via] [--note]`。四道校验：存在、仍待答、选项合法、摘要匹配当前选项。选项内容参与摘要，选项变化则旧答案作废、决策重新上浮。
- 节点转 `blocked_design` 时必须同时有对应的决策记录；没有决策记录的 `blocked_design` 视为生命周期缺陷，按 `supervisor_lifecycle` 处理。
- 渲染：新决策在监工会话立即从盘上渲染一次；未答期间每个降频周期末尾重发一次（带已等待时长）；答案落盘即停。
- 答案落盘后可直接 `vibe resume` 推进，不依赖心跳。

### 5.6 通知桥

按 issue #141 第二层设计，命令来源按 N8：用户级配置给出 `command` 与 `timeout_seconds`，项目 `.vibe/config.json` 只能写 `notify_bridge.enabled`，缺省休眠；新决策落盘时调用一次 `<command> push <决策文件>`；入站只有 `vibe decision-answer`。向导项属于 `sensitive_external` 层，默认不启用；出站推送属于授权卡「对外通信」类，单独列出、默认排除。桥失败记 UNKNOWN，不阻断 run。凭据不入 `.vibe`，决策文件不含文件内容、凭据或隐私。

### 5.7 边界判定与路由

- 打断用户的条件：A §12 的五条与 B1 的两类（新增第三方依赖、执行模式降级为后台不可见）取并集；B1 的验收判定法用于判断 A §12 第 1 条。
- 责任层沿用 A §10 与 D5；挂起与决策类别按 N4。
- #148：分类依据结构化责任层，不再按「权限、授权、安全」等字眼判定；结构化的 `credential_required` 等外部授权信号仍进入需要用户的状态。
- #149：普通报错（读文件失败、摘要文件暂不可读等）不写永久授权失效标记；授权只因授权摘要、计划、合同内容或范围的真实变化而失效。实现前先列出所有可能传到 CLI 失效写入点的异常路径，逐条判定。
- #150：严重度缺失或不规范的 finding 归实现层返工，不升级为产品决策；明确声明会改变验收判定的 finding 仍按 B1 停下。
- #151：`supervisor-hold` 必须声明 N4 类别，并引用决策 ID 或授权缺口；不满足即拒绝挂起。
- #153：协议中「人工/监工处置」改为「监工处置」，并写明三种处置（`confirmed_benign`、`escalated_to_findings`、`resolved_with_facts`）的判定准则；prd-guide §7 按原因列出 `blocked_unknown` 的标准恢复动作并提供重新排队入口；返工 3 轮未收敛时换 reviewer 或拆节点，只有分歧点改变验收判定才升级；reviewer 代改业务代码时作废该轮、退回 developer、换 reviewer；vibe-entry 的「同一方案连续失败 2 次停下重新评分」注明不适用于已授权 run 内的监工。

### 5.8 文件范围与重新授权

## 6. 验收

### 6.1 沿用 A

A1–A13 全部保留，其中：A1 的时限按 N1；A5 的软阈值场景在单班默认开启后同样成立；A13 的口径不变（20 次以上空闲心跳，每次增长不超过 5,000 token，后 10 次平均不超过前 10 次的 1.2 倍或绝对值不超过 500 token）。

### 6.2 决策与通知

- AC-D1：含 `decision_requests` 的 worker 交付使决策落盘、节点转 `blocked_design`、预检输出 `decision`、监工会话渲染卡片。
- AC-D2：会话内 `vibe decision-answer` 后，下一轮或直接 `resume` 推进节点。
- AC-D3：决策未答期间模拟监工失联并接管，新监工开工即从盘上渲染同一决策。
- AC-D4：选项变化后旧答案被拒，决策重新上浮。
- AC-D5：等答期间心跳按 60 分钟运行，答案消费后恢复默认间隔。
- AC-D6：配置通知桥后新决策触发一次调用；桥缺失、超时或失败只记 UNKNOWN，run 不受影响；未配置时无回归；项目配置中写 `command` 被拒绝；含 shell 元字符的路径不会被 shell 解释。
- AC-D7：有交付、结果、请求或 ready 节点时，预检优先输出 `work` 而不是 `decision`。
- AC-D8：旧版心跳指令调用预检时不会收到 `decision`，同一情形收到 `work`。
- AC-D9：注入时钟后，空闲、等答、推送已验证三种情形分别得到 10、60、30 分钟间隔。

### 6.3 边界与宿主

- AC-B1a（§6 补丁批准前）：整合审查返工改两个测试文件自动扩范围、零打断；验收后补丁改 `protocols/__init__.py` 产生一次带具体原因的范围授权请求；其余纯工程问题打断次数为 0。
- AC-B1b（§6 补丁批准后）：上述两种形态都自动扩范围、零打断，事件中有扩展记录与理由。
- AC-B2：#148 报错文本为「authorization digest mismatch」「permission denied writing .vibe/x」时进入可自动恢复状态，结构化 `credential_required` 仍需要用户；#149 读文件失败、摘要暂不可读不写失效标记，合同内容真实变化仍写；#150 严重度缺失或不规范的 finding 进入返工，声明改变验收判定的 finding 仍停下。
- AC-B4（#151）：无类别或未知类别的挂起被拒；两个规范类别及兼容别名都能挂起且落盘为规范值；交接输出显示类别。
- AC-B5（#147）：已验收 A→B，A 只扩文件清单、验收判定不变，重新授权后 B 保持已验收；A 的验收判定变化时 B 照旧失效。
- AC-B6（#153）：三种处置各有判定用例；每种 `blocked_unknown` 原因都有可执行的恢复动作；返工 3 轮未收敛的节点进入换 reviewer 或拆节点，而不是问产品经理。
- AC-B3（反例）：新增第三方依赖、执行模式降级为后台不可见、deploy 三种情形仍然打断产品经理。
- AC-H1：在临时 HOME 下对未初始化项目运行 `init`，对齐门例外决策项必须出现；回答「不应用」可继续且不写任何用户级文件；应用后用户级文件只有标记块变化、留有备份、可回滚，再次运行幂等。测试不得触碰真实用户目录。
- AC-H2：Claude Code 真实能力事实下复杂计划可发布并裁为会话内 SDD；Codex 判定结果与改动前逐字一致；同一份 WorkBuddy 能力事实，改动前裁为 guide、改动后裁为会话内 SDD；没有来源证明或事实为 false 时失败即关闭，回落 guide。

- AC-E1：关掉分诊服务后入口请求按 S1 规则完成分诊并留降级记录；评测报告给出三项数值，ECE ≤ 0.05。
