# Vibe Guide V3.10 PRD / 设计修订（Rev2）

**状态：** `confirmed_pending_authorization`

**确认日期：** 2026-09-02

**上游设计：** [V3.10 PRD / 设计文档](2026-09-02-vibe-guide-v3.10-prd-design.md)

**性质：** 只修订门禁作用域与自动化交付边界；安装、升级、能力扫描、任务分级和版本目标继续沿用上游设计。

## 1. 修订目标

V3.10 的工程规范由产品内部消化，不再把工程完整性问题暴露为产品经理无法继续开发的硬阻塞。监工负责对账、自愈、降级和证据记录；产品经理只在真正的产品决策、外部权限或 Deploy 边界上被打断。

本修订同时保留完整自动化交付闭环：已独立终审通过且 P0–P2 清零的 Issue，可以在用户确认的授权卡范围内自动创建 PR/MR，并自动合并到授权前冻结的目标仓库和目标分支。Deploy 始终不包含在本轮授权内。

## 2. 门禁分层

### 2.1 产品级硬门禁

以下情况需要用户决定，不能由监工猜测或自愈：

- 产品范围、验收目标、外部承诺或授权范围发生变化；
- 需要读取/授予凭据、系统权限或平台登录权限；
- Deploy、生产环境变更、数据破坏或其他明确不可逆操作；
- 授权前无法确定目标仓库、目标分支、Issue/PR/MR 类型、源分支或文件范围；
- 终审未通过、P0–P2 未清零，或需要改变已确认的合并条件。

### 2.2 工程软门禁

以下问题不得阻塞整个 DAG 或无关节点：

- project/host/task identity、visible 定位、worktree/branch 绑定缺证；
- provider create/locate/visibility/lease/cursor 观测缺失、超时或暂态失败；
- 本地工程状态漂移、快照不同步、路径映射缺失或可恢复的合同不一致；
- 某个 Agent 只能以 background/degraded 模式运行。

监工按以下顺序自动处理：复读当前事实 → 对账授权前合同 → 修复绑定/路径/快照 → 续接原任务和 cursor → 在不改变目标的前提下降级到可用执行器 → 记录 `auto_corrected` 或 `degraded`。修复失败只隔离受影响的节点或外部动作，其他 ready 节点继续并行。

### 2.3 外部交付受控动作

创建 PR/MR、`merge_local` 和 `merge_remote` 属于授权卡中的自动化动作，不是产品级硬门禁。它们只能使用授权前冻结的目标合同执行。监工发现运行时漂移时先自动对账和修复；修复后若目标仍能唯一确定且证据满足，即继续执行；只有无法唯一判断或需要改变目标时，暂停该外部动作，不阻塞其他开发、Review、返工和本地验收。

## 3. 授权前目标合同

授权卡生成前，向导必须完成并持久化以下字段：

- provider/远端类型（不预设为 GitHub）；
- 目标仓库或项目、目标分支；
- Issue/PR/MR 类型、源分支；
- 文件范围、合并方法和已确认的非 Deploy 动作；
- 当前计划 revision、Issue 合同摘要和授权摘要。

可从当前开发环境唯一确定的字段自动填充；无法唯一确定时只向用户询问一次。授权后不再反复要求产品经理填写这些工程字段。

## 4. 监工自愈合同

1. 自愈不得扩大文件范围、改变产品目标、切换到未授权仓库/分支或创建第二 writer。
2. 自愈优先复用原 developer/reviewer 任务、worktree、branch、lease、generation 和 cursor；只有原任务已明确终止且满足既有 successor 证据规则时才可恢复。
3. provider 未验证只影响实际依赖该 provider 的节点或动作；本地安装、测试、Review 和可用的其他节点继续推进。
4. 每次自愈追加事件和证据，保留旧证据；用户可见状态只显示“准备中 / 自动修复中 / 已启动 / 需要你决定”。
5. 同一问题可重试和降级，不得因自然语言自报、超时或空响应伪造 provider 成功；但也不得把该未知状态升级为全局 DAG 阻塞。

## 5. 自动创建与合并条件

授权卡默认可列入 `create_pr`、`create_mr`、`merge_local`、`merge_remote`。监工仅在以下条件全部满足时执行相应动作：

1. Issue 有独立 reviewer 终审通过；
2. P0–P2 均为零；
3. developer 交付、Review/返工证据与当前 Issue 合同匹配；
4. 目标仓库、目标分支、源 HEAD、文件范围、计划 revision 和授权摘要与冻结合同匹配；
5. writer lease、任务身份和可用 provider 路径经监工对账或自愈后有效；
6. 动作在用户已确认的授权卡中逐项列明。

创建 PR/MR 和合并的结果必须分别记录；本地合并不得宣称远端合并成功，远端未知只暂停该动作并保留可恢复状态。

## 6. DAG 调度变化

- `depends_on` 只表达真正的产品/数据/接口硬依赖；工程绑定和 provider certification 不得作为所有节点的硬前置。
- 安装、迁移、能力目录、任务分级等本地节点应在无真实 provider 时照常并行开发和验收。
- provider-backed 节点可使用 stub、fixture、fake service 或 background/degraded worker；联调关系用 `integration_after` 表示。
- package/release 节点只依赖本地实现、测试和迁移证据，不依赖真实桌面 provider 生命周期认证。

## 7. 验收标准（新增/修订）

- provider create/locate/visibility 缺证时，本地安装、升级、测试和无关 DAG 节点仍可启动并完成；只记录 `unknown`、`auto_corrected` 或 `degraded`。
- worktree/branch/task identity 漂移可由监工在授权目标不变的前提下自动修复，并保留原任务和证据链。
- 授权前目标字段缺失会在授权卡生成前一次性提示，不会在开发中途首次暴露为阻塞。
- 已终审通过且 P0–P2 清零的 Issue，可按授权卡自动创建 PR/MR 并合并；目标合同漂移由监工先自愈。
- Deploy、凭据、系统权限、数据破坏和改变授权目标仍然无法由普通 DAG 授权自动执行。
- V3.10 本地包的 wheel、sdist、源码安装、升级和回滚验收不因真实 provider 未验证而失败。

## 8. 对上游文档的替换条款

本 Rev2 对上游 PRD 中以下表述作替换：

- “`complex` 首次写入前严格执行绑定门”改为“首次写入前完成目标合同登记；工程绑定由监工在写入路径内部自愈或降级，不阻塞无关节点”。
- “provider pending 只阻塞当前 provider-backed 节点/运行”保留，并扩展到工程绑定、目标漂移和 visible 定位问题。
- “merge 授权不包含 push、创建 PR”改为“创建 PR/MR 可在授权卡逐项列明时自动执行；push、Deploy、凭据和系统权限仍不包含在普通授权中”。
- “任一 merge 前置条件未知都不得合并”改为“监工先按冻结合同自愈；自愈后仍无法唯一确认时，仅暂停该 merge 动作”。

除上述替换外，上游 PRD 的安装、升级、能力授权、版本交付和 V3.9 隔离条款继续有效。

## 9. 实施边界

- 本修订使旧 `vibe-guide-v3.10-rev4` DAG、授权摘要和运行失效；旧运行证据保留，不覆盖、不删除。
- 需重新生成 Spec/Issue/DAG、授权卡和实施计划后，才能开始新一轮监工。
- 本修订不修改 V3.9 Rev4、`E2E_MAILBOX` 或历史 V2 交付证据。
