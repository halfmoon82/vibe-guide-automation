# VibeGuide 规划可追踪适配层设计

状态：设计草案，已纳入 PRD Guide 交互原则，待最终产品审阅
日期：2026-09-15

## 1. 问题

VibeGuide 已经具备 PRD、Spec/Issue、DAG、授权、developer/reviewer 和最终整合 Review，但现有计划主要描述工程任务、文件范围、绑定和测试。它没有强制把产品目标逐项连接到用户场景、代码现状、Issue、实现行为和运行时证据。

因此可能出现两类结果：

- 测试满足实施计划，但实施计划本身已经偏离 PRD；
- 工程门禁和恢复机制正确，却把产品经理无法理解的工程约束变成非预期阻断。

## 2. 目标

在不替换 VibeGuide DAG、授权、监工和 Review 模型的前提下，增加一个规划阶段适配层，使每个复杂计划都产生一份同时面向产品经理和开发者的目标追踪包。

目标追踪包必须回答：

1. PRD 要解决什么用户问题；
2. 当前代码已经有什么、真实入口在哪里、哪些能力可以复用；
3. 每个目标如何落到 Spec、Issue、DAG 节点和代码范围；
4. 预期行为、失败行为和非目标是什么；
5. 最终运行时如何证明用户目标已经实现；
6. 哪些内容是事实、假设、未决产品选择或风险。

## 3. 非目标

- 不引入常驻代码索引数据库或新的后台服务；
- 不替换 VibeGuide 的 Plan、DAG、授权、Monitor、任务绑定或恢复机制；
- 不自动安装外部 Skill；
- 不让规划适配层直接创建 worker、任务线程、Issue、PR/MR 或执行 Git/Deploy；
- 不把 TDD 通过升级为产品目标已实现的证明。
- 不要求用户按固定字段逐项填写 PRD。
- 不把普通信息缺失自动升级为用户阻断。

## 5. 规划产物

每个复杂计划增加一个项目相对路径：

```text
.vibe/plans/<plan-id>/planning-brief.md
```

`planning-brief.md` 使用产品经理可读的正文，并包含以下固定章节：

### 5.1 产品目标

- 目标陈述；
- 用户场景；
- 成功标准；
- 非目标；
- 产品决策和未决选择。

### 5.2 代码现状

- 当前真实入口；
- 已存在的模块、接口和行为；
- 可复用能力；
- 相关测试及其覆盖边界；
- 现状证据路径和符号；
- 不能从代码或测试推断的事项。

### 5.3 变更方案

- 行为变化的前后对照；
- 选择该方案的原因；
- 被拒绝或暂不采用的方案；
- 设计复杂度和阻断风险；
- 需要回到产品决策的事项。

### 5.4 目标追踪矩阵

| Goal | User scenario | Current evidence | Spec | Issue | DAG node | Runtime acceptance |
|---|---|---|---|---|---|---|

每一行必须至少包含一个当前代码证据、一个 Issue/DAG 节点和一个运行时验收方式。无法建立映射的目标不能进入 `authorized`。

### 5.5 开发计划摘要

每个 Issue 只展示产品经理需要理解的内容：

- 要解决的用户结果；
- 修改或复用的代码区域；
- 依赖原因；
- 明确不做什么；
- 完成示例；
- 失败和降级行为；
- 测试与运行时验收。

工程绑定字段继续留在现有 DAG/授权合同中，不在正文中扩散。

## 5.6 PRD Guide 交互原则

PRD Guide 是规划适配层的前置帮助，不是用户填写表单。用户可以只用自然语言描述想解决的问题，系统先结合当前代码现状生成一版 PRD 草案，再把需要人判断的内容收敛成少量产品问题。

字段必须带有来源状态：

- `user_confirmed`：用户明确表达或确认的产品事实/决定；
- `system_inferred`：系统根据需求和代码现状整理出的可逆推断；
- `needs_confirmation`：可能改变产品方向、授权边界或验收含义的内容；
- `unverified`：当前证据不足，不能当成事实。

交互规则：

1. 用户只需描述目标、问题或想要的结果，系统负责先生成初稿；
2. 系统自动补全用户场景、成功标准、失败行为和非目标，并显示其来源状态；
3. 只有 `needs_confirmation` 且会改变产品方向、授权边界或最终验收含义的内容，才向用户提问；
4. 普通缺失项保留为 `system_inferred` 或 `unverified`，继续生成规划材料，不强制用户补齐；
5. 用户可以用一次确认接受整份 PRD，也可以只修改某个关键取舍；
6. 用户确认内容和系统推断内容必须在 PRD、planning brief 和最终 Review 中分开显示；
7. 仍存在实质性产品歧义时才进入 `blocked_design`，不能用测试、工程惯例或 Agent 自报替用户决定。

因此，用户的最小工作路径是：

```text
描述需求 -> 阅读系统整理的 PRD -> 确认或修改关键取舍
```

## 6. VibeGuide 最小接入

优先复用现有结构，不新增独立顶层模型：

- 使用 `Plan.implementation_plan_path` 指向 `planning-brief.md`；
- 在现有 `Plan.integration_contract.integration_acceptance_contract` 中增加 `goal_traceability`；
- 每个 `DAGNode.contract` 增加可选的 `goal_refs`、`current_state_refs` 和 `runtime_acceptance`；
- `ImplementationBrief.goal`、`non_goals`、`call_chain` 和 `invariants` 继续作为 developer 写入前的执行摘要；
- 最终整合 Review 读取同一目标追踪矩阵，不另建第二套产品验收表。

如果现有字段无法承载 `goal_traceability`，才增加一个可选的 `Plan.planning_brief_path` 字段。该字段只保存项目相对路径，不保存绝对路径或凭据。

## 7. 规划流程

```text
PRD
  -> 只读代码现状分析
  -> 产品目标与场景确认
  -> 方案和非目标确认
  -> planning-brief.md
  -> Spec/Issue/DAG
  -> 目标追踪校验
  -> 计划确认与授权
  -> 现有 VibeGuide Monitor
```

规划适配层在生成 Spec/Issue/DAG 前必须完成代码现状分析。它可以提出产品问题，但不能用工程实现自行替用户选择产品方向。

## 8. 阻断与漂移规则

以下情况属于 `blocked_design`，不能进入授权：

- PRD 目标没有用户场景或成功标准；
- 目标没有对应的 Spec、Issue、DAG 节点或运行时验收；
- 计划引入的行为在当前代码中没有明确入口、依赖或替代路径；
- 计划增加的门禁、状态或恢复分支没有对应的产品目的；
- 设计假设与现有代码证据冲突；
- 任务只能用测试通过证明，无法说明真实用户行为如何验收。

以下情况不单独阻断用户：

- 系统仍可用代码和需求上下文形成的可逆推断；
- 普通字段尚未明确，但不会改变产品方向、授权边界或验收语义；
- 失败行为或非目标可以先作为系统推断，并在 planning brief 中标记为待确认；
- 工程实现细节尚未确定，但不影响产品目标确认。

以下情况属于实现阶段漂移，由现有 Monitor/Review 处理：

- 代码改动超出 Issue 的目标或文件范围；
- 实现行为不满足 planning brief 的运行时验收；
- developer 或 reviewer 以工程状态替代产品验收；
- provider、worktree 或任务绑定漂移。

已确认且不改变产品目标的实现纠偏继续沿用现有自动纠偏规则；改变目标、场景、非目标或验收语义时，必须重新生成规划包并使旧授权失效。

## 9. 验收

规划适配层的最小验收包括：

- 每个复杂计划都有 `planning-brief.md`；
- 产品目标、用户场景、非目标和运行时验收可被产品经理直接阅读；
- 每个目标都映射到 Spec、Issue、DAG 节点、代码证据和运行时验收；
- 代码证据引用项目相对路径和符号，不能只写模块名或泛化描述；
- 缺少映射时计划保持 `blocked_design`，不能生成有效授权；
- 现有 simple/light_plan 路径行为不变；
- 规划阶段不创建 worker、任务线程、provider action 或 Git 远端对象；
- 最终整合 Review 能使用同一矩阵验证“目标是否兑现”，而不只验证测试和 diff。

## 10. 方案取舍

### 方案 A：只安装 OpenSpec

成本最低，但需要额外约束 Agent 读取代码，且没有原生的 VibeGuide Issue/DAG 目标追踪。适合作为文档格式参考，不作为主方案。

### 方案 B：完整接入 Shotgun

代码现状理解最强，但引入新的索引和运行时，超出轻度嵌入边界。暂不采用。

### 方案 C：采用 Spec-Driven Develop 的规划方法，VibeGuide 自己生成目标追踪包

保留 VibeGuide 现有运行时和授权边界，只增加一个规划适配层；可以吸收代码分析、任务拆解和 Issue 验收结构，同时把输出改成产品经理可读的目标回链。采用方案 C。
