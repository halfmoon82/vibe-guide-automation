# VibeGuide 5.2.8 PRD r3 独立审阅

审阅者：独立 helper `prd_review_handoff_reader`。日期：2026-11-04。

## 结论

方向与用户决定一致，但发现 **4 项 P1、2 项 P2 的整合契约缺口**；本报告未发现足以认定 P0 的证据。建议补齐下列跨功能裁决后再冻结开发合同，不能仅把 F1–F8 分别实现并以单项测试通过作为整体验收。

这些意见不撤销用户 D1–D6，也不授权开发或改变既有安全规则；大部分属于落实已定规则所需的工程合同细化。需要新增产品取舍的情况在各条中明确标注。

## Findings

### R1 / P1：三次恢复门槛没有区分“不可恢复”与“安全失格后强制更换”

- PRD：156–162 行、223–224 行、270 行。F4 写“至少三次……后才允许考虑 successor”，AC10 写“小于三次不换”，同时要求独立审查保持不变。
- 基线证据：`vibe_guide/monitor.py:7572` 起，reviewer 写业务文件即使本轮审查失格，停止后要求新 reviewer；`:7583` 明确整个 review round 作废，`:7595` 设置 replacement；`:9293` 起另有已结束、验收格式被拒的 reviewer 自动更换路径。
- 反例：reviewer 已越界写业务文件，旧规则要求隔离并更换；按 F4 字面却要先恢复这个已失格 reviewer 三次。若保留旧分支直接换人，又违反 AC10 的无例外判据。
- 影响：安全性/独立性回归，或同一产品规则在不同公开入口有不同门槛。不是建议放松旧安全门。
- 最简解决：定义三次门槛针对“原本仍合格但中断/不可用的同任务恢复”；审查独立性失格、明确安全违规与产品明确批准的任务变更分别沿原有受保护替换流程，不伪造为三次恢复失败。无论原因均要终止/退役证明、唯一 writer 和血缘证据。对旧格式拒收自动替换明确归类，不能默认豁免。
- 验收补充：违规 reviewer 立即失格、不再被恢复；普通中断 reviewer 两次失败仍不换；格式错误不能被用作越过三次门槛的别名。
- 分类：先按既有安全合同细化门槛适用域；如希望三次规则连安全失格也一律覆盖，属于真实产品/安全冲突，必须另行决定，不能由实现自行选择。

### R2 / P1：撤销验收缺少对在途动作和迟到 accepted 的即时隔离规则

- PRD：149–152 行、167–170 行、218 行、232 行。要求正式撤销并复核下游，也要求晚到 timeout 不覆盖有效终态，却未说明撤销后的旧 accepted、旧原生结果和已派发下游如何失效。
- 基线证据：`vibe_guide/monitor.py:1665`、`:4784`–`:4789` 以依赖 status=accepted 作为调度条件；`vibe_guide/state.py:1772`–`:1809` 的验收绑定主要是合同摘要、授权 epoch、reviewer 身份/代次。验收被纠正但合同/授权/任务代次未改变时，这些字段本身不能区分纠正前的迟到结论。
- 反例：A 已 accepted、B 已启动；发现 A 缺真实材料，撤销 A。旧 reviewer 的 accepted 或旧 B 交付稍后到达，F5 去重/终态规则若仍认其有效，就可能再次解锁或接受依据已失效的业务结果。
- 影响：F3 的“不能假解锁”被 F5 的正常迟到处理反向破坏；只在撤销后重新检查 ready 不足以处理已经在途的工作。
- 最简解决：撤销先建立受影响结果的有效性屏障，再允许任何新调度；保留代码和历史证据，但隔离依赖失效材料的在途交付/验收。旧动作回执可对账实际副作用，不得恢复其业务有效性；重验必须明确引用补证后的有效输入和验收轮次。无需强制全 DAG 停止，也不要把所有联调改硬依赖。
- 验收补充：A 撤销与 B 派发并发、撤销后旧 accepted/旧 B 交付迟到、崩溃重放、材料补齐后仅受影响后缀恢复；均不出现一次假解锁或重复 writer。
- 分类：F3/F5/F6 的必要工程合同；不改变原验收标准。

### R3 / P1：旧协议的“采纳后启用”与既有自动刷新直接冲突

- PRD：138 行、267–271 行。新稿替代 daemon 只报告规则，同时要求旧项目物化协议不静默覆盖，未采纳不能宣称全面启用，但未规定混合状态的实际执行规则。
- 基线证据：`vibe_guide/protocols/supervisor-card.md:16` 仍禁止 daemon start；`vibe_guide/initializer.py:209`–`:238` 会自动替换可精确识别的未编辑旧协议；`vibe_guide/cli.py:2705`–`:2722` 在工作命令执行前调用刷新，不只 init 时刷新。编辑过的副本则保留。
- 反例：升级后运行第一个工作命令，未编辑协议被自动刷新而用户未采纳；另一个项目因本地编辑保留“不得恢复”，但新版 daemon/CLI 已开始按新责任运行。两者都可能出现“文件采纳状态”与“实际行为”不一致。
- 影响：新旧职责相互否决，或者发生 PRD 明确禁止的静默规则切换；仅交付补丁并提示不算闭环。
- 最简解决：明确本轮变更对自动刷新机制的例外/迁移路径；在同一 plan/run 的有效合同中记录实际启用的规则版本与采纳状态，覆盖 CLI 输出、监工卡和执行器。未采纳时准确维持已生效合同，不混用新执行逻辑与旧禁止指令；采纳并涉及授权含义改变时走正式重授权。无需覆盖用户编辑内容。
- 验收补充：未编辑旧副本、已编辑副本、拒绝采纳、只采纳部分、运行中升级/重启，均能说明当前究竟执行哪套合同，且不会静默覆盖。
- 分类：与旧版的兼容裁决必须写入 PRD/Spec；“不静默覆盖”方向已经明确，不需再问 D1。

### R4 / P1：监工主动处置与 daemon 旧自愈没有划清同一动作的执行所有权

- PRD：128–140 行、156–170 行、232 行、267 行。监工下一拍必须行动，daemon 又保留机械推进能力；唯一 worker/daemon 并不自动保证“同一个恢复动作只执行一次”。
- 基线证据：`vibe_guide/daemon.py:954`–`:993` 自行评估停滞、调用 retry、启动 level2；`:521`–`:524` 的机械 retry 实际再跑 supervisor.run_once；`:1108`–`:1135` 可启动修复短会话并计 repairs。`:1121`–`:1125` 的 active 标记针对 daemon/短会话，不等价于监工与 daemon 对同一 worker 恢复意图的统一认领。
- 反例：监工已给原 worker 发恢复指令，daemon 同时根据旧 fingerprint 再触发 resume/短会话；两个动作仍操作同一有效 writer，不一定触发“第二 writer”保护，但可重复执行副作用、重复计真实尝试，或由旧恢复结果覆盖新诊断。
- 影响：F1 的因果诊断被旧自动分支打断，F4 三次计数和 F5 幂等可能分别正确却整体错误。现有源码已证明两路执行路径存在，本报告未据此宣称现场已复现该并发。
- 最简解决：明确 daemon 保留哪些无语义副作用的机械动作、哪些动作仅向登记监工移交；所有实际恢复使用同一可恢复的动作身份/认领和当前 owner epoch、任务代次校验。发起和完成只记录一次；接班/重启先对账在途动作，不能简单清空 active 后再发。复用现有 mailbox/租约，不建第二调度器。
- 验收补充：daemon、心跳和换班同时发现同一阻塞，只有一个有效恢复意图；旧 owner 回执可留证但不能推进；计数只增加一次。
- 分类：必要工程整合接口。若要继续保留自动 LLM 短会话，应明确其与登记监工的职责/授权，而非“不是前提”一语带过。

### R5 / P2：init 模型表缺少与既有全局映射和运行时解析的一致性合同

- PRD：182–186 行、229 行。要求生成可维护表、保护人工映射、授权卡准确披露，但未说明表是项目输入还是展示缓存，及其与既有全局 model_map 的优先级。
- 基线证据：`vibe_guide/model_catalog.py:253`–`:266` 仅读取 `$VIBE_HOME/config.json` 的人工 model_map，`:339`–`:371` 再取 alias/cache/probe；`vibe_guide/authorization.py:1782`–`:1802` 生成卡片时解析，`vibe_guide/monitor.py:5728`–`:5733` 在启动时再次解析。
- 反例：init 在项目生成新表但 worker 继续只读全局映射，表可维护却不生效；或者再次 init 刷新后卡片仍披露旧结果、实际派发使用新结果。开发者也可能为使项目表生效反向改写用户级配置，违反人工保护边界。
- 影响：可维护表成为第二事实源，默认模型披露与真实派发不一致。
- 最简解决：明确唯一解析优先级、生成/人工数据所有权、存储作用域和所有消费者；最小方案可以继续沿用现有人工映射，把项目生成表明确为带来源的生成目录/展示，不能不说明用途。刷新不静默改变在途任务；未派发任务的解析变化与当前有效授权/路由规则保持一致并留证。目录缺失不阻授权，不等于非法人工配置可以当作有效配置。
- 验收补充：全局人工配置、生成表冲突、不同项目、授权后再次 init、dev/reviewer 不同档位，doctor/卡片/真实派发结果一致，或准确标出尚未验证/已变化状态。
- 分类：存储与优先级若不改变用户可见语义可在 Spec 细化；若新增项目人工覆盖全局的能力，则是需明确确认的产品选择，不能隐含加入。

### R6 / P2：未知“纯遥测”的机器可判别条件尚未闭合

- PRD：190–193 行、230 行。要求全新 system 遥测可跳过，但专用副作用和血缘不符必须拒绝。system 且无 node_id 不能单独证明“无副作用”。
- 基线证据：`vibe_guide/monitor.py:10489`–`:10517` 目前先按名称跳过部分事件，之后才校验授权/合同；`:10534` 起同样存在 system 级授权变更和特殊投影。`vibe_guide/state.py:1263`–`:1281` 对事件 envelope 使用精确 schema，`:1321`–`:1325` 校验 run，不能假设新增顶层分类字段天然向后兼容。
- 反例：未知 system/无节点事件其实是新版所有权变更，却被旧 reader 当遥测消费；或为避免误吞而对一切未知名称 fail closed，重新造成 #402 类打地鼠。
- 影响：两条 AC 都可能单独实现，组合后不是误吞重要状态，就是仍依赖名称枚举。
- 最简解决：规定由受信任写入路径证明“纯观测”的类别边界，保留专用状态事件先处理和全量血缘检查；未能证明无副作用者保持明确 unknown。旧无分类事件的兼容识别与新增分类的 schema/版本策略在 Spec 中明确，不要求 PRD预定字段名，不允许未校验即前移序号。
- 验收补充：全新可信遥测、未知非遥测 system 事件、伪装类别、旧格式无类别、错误授权/合同混入遥测，均有确定结果，重放不改变。
- 分类：F8 的工程分类和兼容合同，不需改变 D1–D6。

## 已有合理处理、不重复报错的事项

- F2 已明确替代“daemon 死亡只能报告”的产品方向，且保留未知进程不盲启、旧主人保护与连续周期验证；旧条款存在本身不是本次新增缺陷。
- F4 已区别 poll 与真实尝试、成功重置、角色隔离及终止证明，避免直接把既有 retry_scheduled 当三次失败。
- F5 明确 raw 不可变、先认领后 create、形状投影不冒充实际成功；没有承诺可凭补字段伪造回执。
- F3 允许原合同支持的 stub/fixture，不把所有联调强制串行；技术通过不冒充业务完成。
- F6 不把聊天批准当权限事实，要求受保护落地；F7 不把缺目录作为单独授权阻断。
- §10 已明确功能分组不是工程节点，旧卡不覆盖扩大范围，禁止手改 snapshot 或放开 Git 全组绕过限制。

## Spec / Issue / DAG 前必须锁定的整合接口

1. 恢复原因分类、三次门槛适用域、旧安全失格替换入口与统一代次校验（R1）。
2. 验收纠正的有效性屏障、受影响输入/下游集合、在途动作和回执失效判定（R2）。
3. 有效协议版本/采纳状态与运行授权的绑定，以及自动刷新兼容裁决（R3）。
4. daemon/监工共用的恢复动作身份、认领、完成和接班对账（R4）。
5. 模型信息唯一解析路径和刷新时机（R5）；可信遥测分类与旧事件读取（R6）。

按这些共享接口与真实写范围拆工程节点，不能把本报告六项或 F1–F8 直接当六/八个并行节点。集成测试必须跨模块覆盖上述反例，独立终审再检查，而不是等集成时才决定接口。
