## 0. 迭代摘要

**LLM 监工负责发现问题、理解 worker 的处境、从全局诊断并帮助解除阻塞、验证结果和推进 DAG；VibeGuide CLI 提供可信事实、受约束的执行能力与可恢复证据，不以固定错误枚举和重试策略替代监工判断。**

本轮从“四个 issue 补丁 + worker 替换”整合为八项产品能力：

| 编号 | 能力 | 交付结果 |
|---|---|---|
| F1 | 监工诊断与帮助 | 看懂 worker 遇到什么，提供具体帮助并复核，不只催办 |
| F2 | 心跳、自愈与执行器恢复 | 故障有人持续负责，daemon 退出/换班不造成无人推进 |
| F3 | 业务验收与因果推进 | 缺输入不假通过，下游阻塞回到真正责任方 |
| F4 | 实际恢复计数与安全接续 | 普通中断至少三次真实恢复失败后允许接续；安全失格另走受保护替换 |
| F5 | 原生回执适配与对账 | 真实任务结果能进入编排，恢复不重复创建或篡改证据 |

## 3. 目标、成功定义与非目标

### 3.1 目标

1. 监工知道 worker 的具体失败步骤、已试动作和缺失条件，并帮助其恢复。
2. 缺上游输入时协调上游，不机械地给下游派相同返工。
3. 心跳、唤醒、换班继承未完成责任，直到恢复有效、合法等待或真实边界完成移交。
4. 技术测试、任务完成、诚实缺口报告均不能冒充业务验收。
5. 原生副作用不重复执行，原证据不变，恢复不产生第二 writer。
6. 普通工程问题不依赖用户催促；真正的产品/验收变化与新外部授权等边界仍请用户决定。

### 3.2 进展与合法等待

有效进展须与当前问题相关且可验证：正确消费交付/绑定结果、原失败步骤通过、材料补齐、缺陷修复经独立审查、合法派发 ready 节点等。heartbeat exit 0、PID 存活、cursor 改变、升模型、日志增长、已发送建议，不能单独证明阻塞解除或业务完成。

合法等待有具体等待对象、责任方、解除条件和下次检查触发；不是用完整字段包装无限等待。无法安全判断则保留 unknown 并查证，不伪造成功。

### 3.3 非目标

- 不建万能错误枚举、第二套调度器或任意执行后门，不自动跨平台/降级。
- 不无差别读全部会话，不获取隐藏推理、凭据或无关个人数据。
- 不放松验收、删除独立 review 或将缺输入标通过来推动 DAG。
- 不新增依赖、安装 launchd、升级 Agent/运行环境或自动修改外部代理配置。
- 不改样本项目业务代码，不接管或写入其活跃 run。
- 不重做入口评分、换班阈值、模型档位策略、Git 权限粒度；无 GUI 新增/改动。
- 本稿不授权开发 Git 动作或发布/deploy；本次文档提交合并仅按 E2 执行。不承诺费用下降或全平台真测通过。

### 3.4 核心用户场景

- 产品经理授权后离开电脑：worker 报错或 daemon 退出，监工主动查证、恢复并验证，不等待一句“继续”或“修一下”。
- worker 陷入局部误判：监工查看真实上下文，从既有能力和上游产物找到被忽略的路径，帮助原 worker 恢复。
- 节点技术检查通过但业务材料不足：reviewer/监工准确保留缺口并协调补证，不假通过，也不让下游空转。
- 产品经理首次/再次初始化项目：生成信息可维护、人工模型映射不丢；目录缺失时准确披露影响后仍可知情授权。

F1–F8 均属于本轮必需范围，不以优先级名义静默删减。涉及错误验收、安全唯一 writer 和无人推进的反例优先建立失败用例；具体开发顺序在后续 DAG 中按真实依赖和写范围决定。V1/V2 的特殊完成口径见 §8。

## 4. 职责合同

| 角色 | 必须承担 | 边界 |
|---|---|---|
| LLM 监工 | 发现矛盾、看现场、诊断、帮助 worker、协调上游、验证、推进 | 不凭判断扩权限、降验收、写假成功或成为第二 writer |
| CLI/适配器 | 可信状态/证据、原生动作接入、授权/身份/代次/唯一 writer 校验、幂等恢复 | 不用固定次数或错误关键词代替因果诊断；拒绝时给具体未满足条件和证据 |
| developer | 原范围实现/恢复、提交事实与产物、验证建议 | 自报不可用/没权限不是权威能力证据，不伪造完成 |
| reviewer | 独立核对验收、代码和运行证据，区分缺陷与缺输入 | 不代改业务代码，不因测试通过或诚实报告放行 |
| 产品经理 | 决定产品/验收变化、新外部授权等真实边界 | 不承担例行工程排障和保活催办 |

闭环：**观察 → 相关证据 → 根因判断 → 行动/协调 → 结果复核 → 推进或合法等待**。未命中既有故障类别也应继续查证；不确定时定向问原 worker，不猜原因。

## 5. 功能需求（细化均为 system_inferred）

### F1. 看懂阻塞，从全局帮助 worker

1. 对阻塞、review finding、运输失败、超时和停滞，按需查当前合同、失败步骤、预期/实际、工具请求/结果、已试动作及结果、上游产物和缺失条件。
2. 从授权相关的可见消息、工具记录、交付/状态和审查证据取事实，保留来源、时间、角色/任务/代次。摘要不足可定位相关原证据；看不到时说明具体缺口，必要时向原 worker 定向追问。
3. 从节点外核对 worker 前提：是不支持还是调用错误，是代码、输入、绑定、授权还是外部条件。自报“没权限/需安装/不可用”不能直接变成能力或权限结论。
4. 在原授权内查正确用法、给具体建议、协调上游、安排原 worker 执行，不只转报错/说再试一次；不要求监工代改业务代码。
5. 核验原失败是否消失、缺口是否填补。建议发送、已读或新 turn 不等于解决；无效须更新诊断，不重复同证据同动作。
6. 未完成问题可恢复出事实、判断及不确定性、已试行动、责任方、下一动作和复核条件。复用现有记录，不把新增故障表单当所有工作的前置门。
7. 只提供必要安全摘要和按需引用，不默认装载整份会话，不输出敏感原文。

### F2. 心跳履责、同平台自愈、daemon 与换班

1. 故障交计划实际平台的登记监工；Codex run 无 Claude 也不调用 Claude，不自动跨平台、不以额外短会话为前提、不等六小时才报告。
2. 可见故障在下一有效心跳/唤醒开始诊断或执行已有下一动作；不是只跑完命令。长动作允许跨回合，责任和验证跟随，不要求一拍内全部修好。
3. 通知去重只影响通知，不停止处理/复核。DONT_NOTIFY 不等于 idle、健康或问题已解决。正常 idle 仍增量轻量，不反复全量读历史。
4. **替代本轮相关旧规则“daemon 失活只上报，恢复只能归 launchd/产品经理”。** 同 run 普通恢复已授权、当前 owner 有效、可证明无并行冲突时，监工可安全恢复 daemon，无需再催。
5. 先核对进程、租约、owner 和原启动事实。旧进程未知或身份未验证时 fail closed 并查证，不盲启第二个 daemon，不伪造/清空身份；安装 launchd、新系统权限仍单独批准。
6. 换班须交接实际执行身份、登记、租约和未完成责任。旧主人保护仍有效；不能只查 PID 瞬时存在，须验证新主人下**至少两个连续调度周期**有效，且有与可服务事项相符的行动/等待结果。
7. daemon 稳定定位 VibeGuide 自身运行时，不被业务 cwd 同名包/旧版本遮蔽，不要求改业务仓库加转发文件；定位未知不能报启动成功。
8. 监工不可达、通知失败或查询超时保留 unknown 与待办，不解释为无事/成功，不自动换平台。
9. daemon 保留已授权 DAG 调度、事实采集、结果消费、去重通知和执行已认领动作；需要因果诊断、恢复方案或新恢复尝试时交登记监工，不再自行按停滞次数启动平行 LLM 修复短会话。监工决定、执行器执行复用同一 mailbox/租约，不建第二调度器。
10. 监工、daemon、心跳和接班对同一问题使用稳定恢复动作身份与唯一认领，绑定当前 owner epoch、任务角色/代次及授权/合同。发起和完成只记录一次；普通调度/轮询不计恢复尝试。认领未决或调用超时先对账副作用，不清空 active 后重发；旧 owner 结果可留证、核验和对账，不能自行推进当前状态。换班先接续在途动作再决定新动作（联动 F4/F5）。

### F3. 业务验收、输入就绪与因果推进

1. 分清交付、技术检查、业务验收。对原必需验收例子记录满足/未满足/未知及证据关联；不强制新增同名状态，但机器可检查必需项是否覆盖。
2. accepted 事件、P0–P2 清零、测试通过、诚实 needs_input 都不能单独放行。必需项未满足/未知、证据缺失或显式矛盾时不登记业务通过。CLI 查显式一致性，reviewer/监工承担语义判断，不要求 CLI 理解全部自然语言。
3. 原合同要求真实材料时，不能用静态报告、fixture、自报替代。结构性待验可单列，但不能借此放过必需业务项。
4. 缺上游材料追溯责任方并补证/恢复。原授权内、验收不变的纠偏只修受影响后缀，保留无关成果；范围/验收变化照常确认。
5. 代码缺陷退原 developer，运输故障走恢复。不得因 reviewer 提出真实缺口而换人求通过，不按返工次数自动推定模型/审查者有问题。
6. 已验收后发现矛盾，先持久记录验收撤销及受影响输入/结果的有效性屏障，再允许任何新派发或验收；该屏障在调度、结果消费及崩溃重放中一致生效。未能确定影响集合时暂停可能受影响的派发/验收并查证，不能把 unknown 当无影响。旧事件、代码及交付保留，无关锁定成果不重做。
7. 依赖真实材料的下游不能假解锁；允许原合同支持的 stub/fixture 独立开发，不把所有联调关系变硬依赖，其业务验收仍需原证据。输入未变不反复派同一无效工作。
8. 已在途的受影响下游不因撤销自动丢成果或创建新 writer；隔离依赖失效输入的交付/验收，监工判定可独立继续的工作与必须安全暂停的工作。旧 accepted、旧下游交付及原生回执只能留证/对账实际副作用，不得跨越屏障恢复业务有效性。补证后重验须绑定有效输入版本和当前验收轮次，再按原合同恢复受影响后缀；不能仅因合同摘要、授权或任务代次没变就采信旧结论。

### F4. 三次实际恢复失败后的安全接续

1. 对仍具资格但普通中断/不可用的原任务优先恢复；连续**至少三次真实发起、已完成且失败的恢复尝试**后才允许考虑 successor；是允许，不是第三拍强制换人。该门槛不用于要求恢复已安全失格的执行者。
2. 计数按 run/节点/角色/原任务隔离，同一尝试稳定关联；tick、相同观察、重复回调、重启/重放不增加。查询超时没得到恢复结果，不当已完成失败。
3. 成功重置连续失败数，新任务不继承；缺上游材料、review 不通过和业务 P1 不属于 worker 恢复失败。旧 attempt 无法证明实际尝试时保留未分类，不反推门槛。
4. 三次失败不证明死亡。新派发前验证旧任务终止、绑定退役、写租约释放；unknown/timeout/自报不构成终止证据。
5. 保持原业务合同、平台/可见性、指定 writer worktree/branch 和已有成果；核对冻结 HEAD，留存未提交成果并确认安全接续状态，不丢改动来“清场”。host worktree 不能替代合同 writer root。
6. 保留旧身份/cursor、尝试结果、终止证据、代次和新旧关联；最多一个有效 successor；旧迟到回报不覆盖新代次。
7. developer/reviewer 均按真实平台/拓扑/血缘恢复，公开入口不能把 visible 送 background，也不能 active_role 清空后误找 developer。原 visible-sdd/dual-visible 审查独立性不变。
8. 已证实的安全违规/审查独立性失格立即隔离，其审查结论失效，不恢复该失格执行者来凑三次；沿既有受保护替换流程保留失格事实。用户明确批准的任务变更另按其有效新合同处理，不伪造为恢复失败。无论普通 successor、安全替换还是批准的任务变更，均必须满足终止/退役、写权释放、成果保护、身份血缘和可见性约束；未知终止状态仍禁止新派发。
9. 单纯格式拒收、review 不通过、返工轮数或真实材料缺口不等于安全失格，也不能直接换 reviewer 求通过。可续接时由原 reviewer 更正；确属普通不可恢复时按本节三次门槛。旧格式拒收自动换人与旧修复入口不得绕过该分类或沿用轮询计数。

### F5. 原生回执接入与可重放对账

1. 正式适配路径连接原生返回与 CLI 结构，覆盖本轮 create/resume/定位/可见性/等待结果；不需 run 专用 subclass。
2. 首份 raw 和冲突观察保留，不覆写失败、wake_failed 或原结构。规范投影绑定 action/request digest、实际任务、角色/代次、授权/合同并引用 raw；不能只补 resumed=true 就宣称成功。
3. create 已有真实任务、登记中断时先认领/对账原任务，不再 create；先消费已有结果再发下一动作。形状修正不重做副作用。
4. 中断后投影可重建、校验和幂等消费；shape 通过不是授权/绑定通过。没原生成功证据则保持 unknown。
5. 同交付/finding 重复到达不重复推进/计返工；晚到 timeout 不覆盖当前仍有效的终态。“有效”必须同时通过 F3 的输入/验收屏障、当前身份代次及授权校验，已撤销结论不受终态保护。动作对账成功不等于业务有效性恢复；旧 owner/旧轮次回执不自行推进。样本重入根因未完全验证，按一般幂等要求验收，不虚报新缺陷。

### F6. 工程阻塞上报与许可落地

1. 初次/续接/返工 dev/reviewer 指引均有与实际校验一致的 blocked_engineering 示例，报告失败步骤、已试结果、缺口/证据并唤醒监工，不需伪造 complete/accepted。
2. 上报进入 F1，允许必要追问，不只转发，不强迫冗长模板。
3. 工程聊天不自动变权限。scope/合同许可有明确受保护落地路径：校验当前授权、项目规则、占用、唯一 writer；成功后范围及后续投影一致，保留决定来源/事件。
4. 无权不能答复已批准；越规则时说明具体缺什么批准，不将临时扩大全局 auto_scope_paths 当默认修法。
5. 有效决定一次落地、适用后代继承；失败不假报“已批准”；真实合同变化仍更新授权，不借其他项目开关或增加 .gitignore 全局豁免。

### F7. 初始化模型表与知情授权（#397）

1. 经确认的 init 尽力依据真实可用目录/配置建可维护表，说明来源、生成部分和手填 model_map；CLI 不依赖仅宿主可调用的 create_thread 来取目录。
2. 再次 init 刷新生成信息，保留人工映射/规则/无关配置；相同输入幂等，冲突披露不静默覆盖。超时/缺失/过期不能伪装验证成功。
3. doctor/授权卡准确说明哪些 worker/档位将用默认模型；全部受影响才写所有 worker。有效人工映射仍生效。
4. 缺目录本身不阻授权，披露后可继续；真实能力/身份/授权门禁不受此豁免。发现不一致可再次 init 刷新，保护人工优先权。
5. 模型表不存凭据/绝对个人路径，不未经确认改用户级配置；已有手填方式继续可用。
6. 本轮采用最小兼容方案：人工模型输入继续唯一来自既有 `$VIBE_HOME/config.json` 的有效 `model_map`；项目生成表是带来源、生成时间和验证状态的目录/解析结果展示，不新增项目人工覆盖全局的输入层，不反向写用户级配置。需要人工调整时沿现有 `model_map` 路径维护，已人工编辑的项目表保留并提示其不是派发输入。
7. 唯一解析优先级保持“有效人工映射 → 平台既有别名或有效目录缓存/探针 → 平台默认模型”，非法人工配置按既有错误合同报明，不能冒充缺目录降为有效。init、doctor、授权卡及实际 dev/reviewer 派发使用同一解析语义；不同项目不因生成表互相改写人工设置。
8. 再次 init 仅刷新生成信息，不改变在途任务已绑定模型。未派发任务的解析与授权披露发生漂移时，先披露差异并按有效路由/授权合同留痕处理；允许自动路由的沿其受保护路径更新，不允许的暂停相关派发并重授权，不以再次 init 静默放行或扩大所有任务的授权。

### F8. 通用系统遥测恢复（#402）

1. 先以 supervisor_beat_rejected 无 node_id 复现 unknown node，再修类别规则，不逐名补漏。
2. 纯 system、无 node_id、无业务/授权副作用的遥测只推进已验证序号；新增未登记名字同样不阻断，不改节点。
3. 专用授权/变更及需状态投影的 system 事件仍正常处理，不能一律吞掉。非 system 缺节点、错误节点、run/授权/合同/血缘不符仍拒绝。
4. 快照恢复/重复重放幂等、原事件保留，不跳证据校验。
5. `system`、无 `node_id` 只是必要条件，不是“纯遥测”的充分证据。新遥测须由受信任的观测写入路径与受校验事件格式证明不产生状态/授权副作用；不信任任意 payload 自标“telemetry”。专用状态/授权事件优先走专用处理；未知且无法证明纯观测的事件保留明确 unknown，不消费其序号。
6. 旧格式通过受保护的兼容读取路径识别已知生产语义，不改 raw、不伪造分类；无充分依据者保持 unknown。新格式的 schema/版本和新旧 reader 兼容由 Spec 锁定，不直接塞新顶层字段破坏精确 schema。新遥测类别一次定义、后续新增名称不逐名登记；所有类别都先验证 run/授权/合同血缘，再前移序号，拒绝伪装类别或错血缘。

## 6. 人类参与与安全边界

| 情况 | 必须怎样处理 |
|---|---|
| 原授权内工程问题 | 监工查证、行动、复核；不因不认识格式就交用户 |
| 输入缺失 | 协调正确责任方；确需用户时给具体缺口/最小操作/解除验证，不无限返工 |
| 产品/验收含义变化 | 暂停受影响后缀、确认并更新授权，不降标准 |
| 新外部授权、凭据、系统权限、deploy/发布、生产写入、对外通信 | 对应独立授权和能力验证，不借自愈执行 |
| 新依赖或可见降级后台 | 按当前项目规则单独确认，不以披露替代批准 |
| 旧执行者状态未知 | 保留具体 unknown、继续查证，不开第二 writer/daemon |

按实际动作/证据分类，不靠权限字眼，也不让 LLM 自报取消安全门。通知失败不等于已送达；移交有可定位待办、责任对象及解除条件，不能一句“需要人”结束。
